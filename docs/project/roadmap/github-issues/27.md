title: Add a shared query timeout for HTTP and MCP

Long-running queries currently have no server-side execution deadline. Stopping an async wait does not stop the blocking query computation.

Add the same optional CLI setting to both interfaces:

```sh
sparqld /path/to/data --query-timeout 20
sparqld mcp /path/to/data --query-timeout 20
```

Use one shared execution policy rather than separate timeout implementations in the HTTP and MCP adapters. Leaving the option unset preserves unlimited execution.

Acceptance:
- Parse a positive whole number of seconds and reject zero, invalid and overflowing values.
- Give each query an absolute deadline and an Oxigraph cancellation token. Cover planning, evaluation, full result iteration and server-side response preparation; define startup, input-reading and network-write boundaries consistently.
- Signal engine cancellation when the budget expires. Discard buffered partial results and check the absolute deadline immediately before publishing success, including ASK and MCP output packing.
- Return an explicit timeout error through both interfaces. Proposed encoding: HTTP 503 with a query-timeout message; MCP tool result with isError=true and the same reason. Keep client cancellation distinct from deadline expiry.
- Bridge MCP request cancellation and handler cleanup to engine cancellation. Do not rely on dropping or timing out spawn_blocking.
- Remove completed deadline registrations and retain worker/resource accounting until execution actually stops and releases dataset access.
- Test HTTP/MCP parity, SELECT/ASK/graph cancellation, late timer delivery, independent concurrent deadlines, a successful query after a timeout, and reload progress after cancellation.

Oxigraph 0.5.9 already exposes SparqlEvaluator::with_cancellation_token, so engine cancellation does not require a dependency upgrade. A temporary probe stopped evaluation at a 100 ms deadline. However, cancelled ASK/EXISTS probes on 0.5.9 and 0.5.12 returned a successful boolean with the token already cancelled. A final deadline/cancellation check is therefore necessary even if evaluation returns success.

Document that cancellation is cooperative: sorting and other work between engine checkpoints may overshoot. A strict process-termination boundary would require isolated query workers and is separate architectural work.
