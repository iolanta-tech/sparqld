The dataset is shared as `Arc<RwLock<Store>>` (`SharedDataset`), but the lock protects nothing that Oxigraph does not already guarantee.

Why it is unnecessary:

- `oxigraph::store::Store` is `Clone` (a handle to shared storage) and thread-safe. Its in-memory backend gives each query a consistent snapshot while writes proceed.
- Watch-mode reloads already mutate the store in place under a *read* guard (`watcher::reload`), relying on that guarantee rather than on the lock.
- The only write-lock acquisition is `reload_dataset` in `src/lib.rs`, which swaps in a freshly loaded store. It runs only during initial load (both `--no-watch` and watch mode via `DirectoryWatcher::start_with_patterns`), before `StartupGate` is marked ready.
- HTTP and MCP queries wait on `StartupGate` before taking the read lock, so once a query reaches the lock no writer can exist. Acquisition never blocks; it only adds poisoning error paths and a lock-wait boundary that has to be reasoned about.

Proposal:

Have the initial load publish its finished `Store` through the startup gate (for example a `OnceLock<Store>`, or a gate that carries the store on `Ready`), and give queries and the watcher a `Store` clone instead of a lock guard.

Acceptance:

- Remove `RwLock` from `SharedDataset` and all `read()`/`write()` call sites in `server.rs`, `mcp.rs`, `watcher.rs` and `lib.rs`, together with their lock-poisoning error handling.
- Preserve startup behaviour: queries wait until the initial load finishes and receive the existing error if it fails.
- Existing HTTP, MCP and watcher tests pass; reload visibility tests still observe in-place updates.

This also removes the lock-wait boundary from the query-timeout design in https://github.com/iolanta-tech/sparqld/issues/27.
